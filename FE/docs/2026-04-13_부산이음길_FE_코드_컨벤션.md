## 2. 레퍼런스 비교 분석

### 2.1 온보딩 코드_성현 폴더의 장점

- 단일 모듈에서 `ui/data/di`를 분리해 초반 진입 장벽이 낮다.
- `StateFlow + collectAsState()` 흐름이 명확하고, `Intent/State/ViewModel` 패턴이 빠르게 복제 가능하다.
- `Repository`가 온라인/오프라인 분기를 숨기고 있어 발표용 fallback 구조를 설명하기 쉽다.
- `ui/component`, `ui/theme`를 먼저 만든 뒤 화면에 붙이는 흐름은 팀 초반 생산성에 유리하다.

### 2.2 온보딩 코드_성현 폴더의 한계

- `frontend/ui/MainActivity.kt`에 라우팅, 권한 요청, 초기화, 화면 등록이 과도하게 집중돼 있다.
- `frontend/data/repository/GestureRepository.kt`처럼 리포지토리 하나가 너무 많은 책임을 가지는 구조는 현재 프로젝트에서도 그대로 가져오면 빠르게 비대해진다.
- `ui/component/TemplateLayouts.kt` 같은 공통 템플릿은 유용하지만, 화면 특성이 다른 지도형 앱에 그대로 적용하면 오히려 제약이 된다.
- 패키지/파일 규칙이 문서상 템플릿과 실제 코드에서 완전히 일치하지 않는다. 그대로 복사하면 "문서상 구조"와 "실제 구조"가 다시 벌어진다.

### 2.3 특화 프로젝트 S14P21E106 FE 구조의 장점

- `app/core/data/di/feature` 구조가 현재 프로젝트에 가장 가깝다.
- `app/navigation/AppNavHost.kt`, `AuthNavGraph.kt`, `HomeNavGraph.kt`, `SettingsNavGraph.kt`처럼 NavGraph를 분리해 `MainActivity`를 얇게 유지한 점은 바로 채택할 가치가 있다.
- `feature/*Contract.kt`에 `UiState`, `UiEffect`, `Intent`를 모으는 방식은 파일 수를 과도하게 늘리지 않으면서도 상태 패턴을 고정하기 좋다.
- `core/ui/component/*`, `core/ui/theme/*`처럼 토큰과 공통 컴포넌트를 기능 코드와 분리한 점은 피그마 병행 작업에 유리하다.
- `docs/maintenance/2026-03-28_FE_디자인시스템_구현기준_및_문서정합성.md`처럼 "현재 구현 기준"과 "목표 기준"을 분리해 기록한 점은 실무적으로 좋다.

### 2.4 특화 프로젝트 S14P21E106 FE 구조의 한계

- 컴포넌트 계층이 깊고 범위가 넓다. 지금 프로젝트 일정에서 처음부터 같은 깊이로 시작하면 문서만 많고 화면은 늦어진다.
- 실제 문서에서 이미 "문서와 구현의 불일치"를 별도 문서로 관리하고 있다. 이 자체가 나쁜 것은 아니지만, 지금 프로젝트에서 같은 수준의 문서 체계를 초반부터 만들면 운영비가 크다.
- 공통 컴포넌트가 많아질수록 예외 스타일이 feature 내부에서 다시 생겼다. 지도형 서비스도 같은 실수를 반복할 가능성이 높다.
- 현재 서비스 색상/브랜드 규칙은 구독 관리 앱에 맞춰져 있다. 부산이음길에 그대로 가져오면 서비스 성격이 맞지 않는다.

### 2.5 두 레퍼런스에서 공통으로 가져갈 패턴

- 단일 `app` 모듈로 시작한다.
- `app / core / data / di / feature` 패키지 구조를 쓴다.
- `MainActivity`는 앱 진입과 `AppNavHost` 호출만 담당한다.
- `Route -> Screen -> ViewModel -> Repository` 흐름을 고정한다.
- `UiState + UiAction + UiEvent` 단방향 상태 패턴을 쓴다.
- 공통 UI는 primitive부터 만들고, feature 특화 컴포넌트는 재사용 근거가 있을 때만 올린다.

### 2.6 현재 프로젝트 일정상 버려야 할 과설계

- 멀티모듈 분리
- `domain/usecase` 계층을 feature마다 전부 만드는 구조
- 모든 리포지토리에 인터페이스/구현체 쌍을 강제하는 구조
- 지도 SDK를 완전히 추상화한 범용 지도 엔진 계층
- 초기부터 30개 이상 공통 컴포넌트를 만드는 디자인 시스템 선구축
- 다크 모드 동시 지원
- 화면 하나에서만 쓰는 UI를 `core`로 끌어올리는 습관

### 2.7 지금 가장 먼저 고정해야 할 뼈대

### 4.5 Compose 함수 네이밍 규칙

- `@Composable` 함수는 PascalCase를 쓴다.
- `Route`는 ViewModel 연결과 side-effect만 담당한다.
- `Screen`은 순수 UI 렌더링과 콜백 인자만 가진다.
- 공통 컴포넌트는 `Eum` 접두어를 쓴다.
- feature 전용 composite는 feature 도메인 명사를 앞에 둔다.

```kotlin
@Composable
fun MapRoute(
    onNavigateToSearch: () -> Unit,
    viewModel: MapViewModel = hiltViewModel(),
) { ... }

@Composable
fun MapScreen(
    uiState: MapUiState,
    onAction: (MapUiAction) -> Unit,
) { ... }

@Composable
fun EumButton(...) { ... }

@Composable
fun MapPlaceDetailSheet(...) { ... }
```

### 4.6 ViewModel / State / Action / Event 네이밍 규칙

기본 규칙은 `Contract` 파일 하나에 상태/액션/이벤트를 묶는 방식이다.

```kotlin
// feature/map/MapContract.kt
data class MapUiState(
    val isLoading: Boolean = false,
    val markers: List<PlaceMarkerUiModel> = emptyList(),
    val selectedPlace: PlaceSummaryUiModel? = null,
)

sealed interface MapUiAction {
    data object Load : MapUiAction
    data class FilterToggled(val category: PlaceCategory) : MapUiAction
    data class MarkerClicked(val placeId: String) : MapUiAction
}

sealed interface MapUiEvent {
    data class ShowSnackbar(val message: String) : MapUiEvent
    data object NavigateToSearch : MapUiEvent
}
```

#### 규칙

- `UiState`는 화면이 그리는 데이터만 가진다.
- `UiAction`은 사용자 입력만 가진다.
- `UiEvent`는 일회성 처리만 가진다.
- Android `Intent`와 혼동을 피하기 위해 기본 용어는 `UiAction`으로 통일한다.
- `MutableStateFlow`, `MutableSharedFlow`는 ViewModel 내부에서만 사용한다.

### 4.7 DTO / Entity / Domain / UI Model 네이밍 규칙

| 층위 | 규칙 | 예시 |
| --- | --- | --- |
| DTO | API 계약 그대로 반영, suffix `Dto` 필수 | `RouteSearchResponseDto` |
| Entity | Room/DataStore 저장 모델, suffix `Entity` 필수 | `BookmarkPlaceEntity` |
| Domain Model | 비즈니스 기준 모델, suffix 생략 | `Place`, `RouteOption`, `HazardReport` |
| UI Model | 화면에 맞춘 표현 모델, suffix `UiModel` 필수 | `PlaceDetailUiModel`, `SavedRouteItemUiModel` |

#### 금지

- DTO를 ViewModel이나 Screen까지 직접 올리는 것
- Entity를 화면 상태로 직접 쓰는 것
- 도메인 모델과 UI 모델을 구분하지 않고 한 클래스에 모두 우겨 넣는 것

### 4.8 Route / NavGraph 네이밍 규칙

- 타입 세이프 라우트를 기본으로 쓴다.
- `Route.kt`에서 route 타입을 정의하고, 그래프 파일은 목적별로만 나눈다.
- route 이름은 화면 라벨이 아니라 도메인 동사/명사로 정한다.

```kotlin
sealed interface AppRoute

sealed interface OnboardingRoute : AppRoute {
    @Serializable data object OnboardingType : OnboardingRoute
    @Serializable data object OnboardingLevel : OnboardingRoute
    @Serializable data object LocationTerms : OnboardingRoute
}

sealed interface MainRoute : AppRoute {
    @Serializable data object Map : MainRoute
    @Serializable data object Search : MainRoute
    @Serializable data class RoutePreview(val placeId: String) : MainRoute
}
```

#### 금지

- `MainActivity` 내부에 모든 `composable(...)` 등록
- 문자열 route 하드코딩
- 하나의 `AppNavHost.kt`에 300줄 이상 라우트 등록

### 4.9 Repository / DataSource / Manager 역할 경계

| 역할 | 반드시 하는 일 | 하면 안 되는 일 |
| --- | --- | --- |
| Repository | remote/local/mock 선택, mapper 호출, cache/fallback 정책, sync 정책 | Compose 상태 관리, `NavController` 호출, SDK UI 직접 제어 |
| RemoteDataSource | API 호출, SDK 네트워크 호출, 응답 수신 | fallback 분기, Room 저장, UI 메시지 생성 |
| LocalDataSource | Room/DataStore CRUD | API 호출, UI 모델 생성 |
| MockDataSource | 데모 fixture 반환 | 실제 저장 성공인 척 write 처리 |
| Manager | TTS, 위치, 권한, 센서, 시스템 서비스 래핑 | 비즈니스 분기, repository 대체 |

#### Repository 기본 형태

```kotlin
class PlaceRepository @Inject constructor(
    private val remote: PlaceRemoteDataSource,
    private val local: PlaceLocalDataSource,
    private val mock: PlaceMockDataSource,
    private val policy: DataSourcePolicy,
) {
    suspend fun getNearbyPlaces(query: PlaceQuery): List<Place> {
        if (policy.forceMock()) return mock.getNearbyPlaces(query)

        return runCatching {
            val remoteResult = remote.getNearbyPlaces(query)
            local.savePlaceCache(remoteResult)
            remoteResult
        }.getOrElse {
            local.getPlaceCache(query).ifEmpty {
                mock.getNearbyPlaces(query)
            }
        }
    }
}
```

### 4.10 UI에서 금지할 것

- Retrofit, Room, DataStore 직접 호출
- `remember { mutableStateOf(...) }`로 서버/로컬 원본 상태를 들고 있는 것
- 하드코딩된 색상, `dp`, `sp`, 문자열 남발
- `NavController`를 `Screen`까지 끌고 들어가는 것
- 지도 SDK 타입을 feature 밖으로 노출하는 것
- `Toast`를 화면 곳곳에서 직접 호출하는 것

### 4.11 ViewModel에서 금지할 것

- `Activity`, `Context`, `NavController` 보관
- DTO/Entity를 그대로 `UiState`에 노출
- 로컬/원격/mock 분기를 ViewModel에서 직접 처리
- 화면 문구를 하드코딩한 긴 문자열 생성
- 여러 feature의 상태를 한 ViewModel에 몰아넣는 것

### 4.12 디자인 토큰 관리 규칙

- 토큰은 `core/designsystem/token` 아래에서만 관리한다.
- 최소 토큰은 `Color`, `Typography`, `Spacing`, `Radius`, `Elevation`, `IconSize` 여섯 종류다.
- UI 코드에서 raw hex color 사용 금지다.
- UI 코드에서 raw spacing 값 사용은 예외가 아니라 금지다. 필요하면 토큰을 먼저 만든다.
- 시각장애/보행약자 모드에 따른 강조 차이는 screen에서 분기하지 말고 token 또는 semantic style로 분리한다.

### 4.13 문자열 / 리소스 / 아이콘 관리 규칙

- 사용자에게 보이는 문자열은 전부 `strings.xml`에 둔다.
- TalkBack용 라벨도 문자열 리소스로 관리한다.
- 지도 시설/카테고리 아이콘은 `res/drawable/ic_place_*` 규칙으로 관리한다.
- Material 기본 아이콘은 내부 제어용에 한해 사용하고, 도메인 아이콘은 서비스 자산으로 관리한다.
- placeholder 이미지, 더미 텍스트도 preview 전용이 아니면 production 리소스 위치를 정한다.

### 4.14 로컬 저장과 API 연동 분기 규칙

| 도메인 | 기본 저장소 | 읽기 규칙 | 쓰기 규칙 |
| --- | --- | --- | --- |
| 온보딩 / 위치약관 / 접근성 설정 / TTS 설정 | DataStore | local only | local only |
| 북마크 / 자주 가는 길 / 최근 검색 / 제보 draft | Room | local first | local write 후 선택적 sync |
| 장소 마커 / 장소 상세 / 경로 탐색 | remote + cache + mock | remote 우선, 실패 시 cache, 없으면 mock | 읽기 전용 cache 저장 |
| 제보 제출 | remote | draft 있으면 로드 후 remote 제출 | remote 실패 시 draft 유지 |

#### 기본 규칙

- UI는 로그인 여부로 저장 위치를 직접 분기하지 않는다.
- Repository가 `local only`와 `local + sync`를 결정한다.
- 비로그인 MVP 기준의 source of truth는 로컬이다.

### 4.15 Mock 데이터와 fallback 규칙

- 발표 필수 read API는 `remote -> local cache -> mock` 순서를 기본으로 한다.
- `forceMock`는 debug build에서만 켠다.
- write API는 실패 시 "성공처럼 보이게" 처리하지 않는다.
- 단, 제보 draft, 최근 검색, 북마크, 자주 가는 길은 local write를 먼저 성공시키고 sync 상태를 별도로 둔다.
- mock fixture는 feature마다 흩뿌리지 말고 `data/mock/fixture`에 모은다.
- mock 모델도 domain model 기준으로 반환한다. DTO를 mock으로 직접 쓰지 않는다.

### 4.16 Preview 작성 규칙

- 공통 primitive 컴포넌트는 최소 2개 preview를 둔다.
  - 기본 상태
  - 상태가 있는 경우 disabled / selected / error 중 1개
- Screen은 최소 2개 preview를 둔다.
  - 기본 상태
  - loading / empty / error 중 1개
- 지도 화면 preview는 실제 SDK 지도를 띄우지 않는다. placeholder surface와 fake marker data를 쓴다.
- preview 데이터는 `core/designsystem/preview` 또는 feature 내부 `preview` 패키지에 둔다.

### 4.17 테스트 최소 기준

- ViewModel마다 최소 2개 단위 테스트
  - 정상 로드
  - 실패 또는 fallback
- Repository마다 최소 1개 source selection 테스트
  - remote 성공
  - remote 실패 시 local/mock fallback
- Compose UI 테스트는 최소 아래 3개를 우선 적용한다.
  - 온보딩 선택 상태 전환
  - 약관 동의 버튼 활성화
  - 지도 필터 선택 상태
- 접근성 수동 점검은 아래 화면에서 필수다.
  - 지도 메인
  - 시설 상세 시트
  - 경로 설정
  - 내비게이션 진행
  - 제보 화면

### 4.18 문서화 규칙

- FE 전용 문서는 `FE/docs`에만 둔다.
- 구현이 문서에서 벗어나면 같은 작업 주기에 문서를 갱신한다.
- "현재 구현 기준"과 "목표 기준"이 다르면 한 문서 안에서 구분한다. 문서를 두 개로 복제하지 않는다.
- feature별 임시 메모, 회의록, 캡처 문서는 활성 문서로 두지 않는다. 필요 시 `archive` 성격으로 분리한다.

## 5. 이번 주 바로 고정할 규칙 Top 15

1. `MainActivity`는 `AppNavHost`만 호출한다.
2. 패키지 구조는 `app/core/data/di/feature`로 고정한다.
3. feature 기본 파일은 `Contract/Route/Screen/ViewModel` 네 개로 시작한다.
4. `UiAction` 용어를 기본으로 쓴다. `Intent`는 쓰지 않는다.
5. `Route`는 ViewModel 연결만, `Screen`은 순수 UI만 담당한다.
6. 화면은 Repository를 직접 모르면 된다.
7. DTO와 Entity는 절대 `UiState`에 올리지 않는다.
8. 온보딩/설정은 DataStore, 북마크/자주 가는 길/최근 검색은 Room으로 간다.
9. read API는 `remote -> cache -> mock`, write API는 local draft 또는 명시적 실패로 처리한다.
10. 공통 컴포넌트는 primitive와 지도 composite까지만 만든다.
11. `Eum` 접두어 없는 공통 컴포넌트는 만들지 않는다.
12. 사용자 노출 문자열과 접근성 라벨은 전부 리소스로 뺀다.
13. 아이콘 버튼은 최소 `48dp`, 핵심 액션 버튼은 최소 `56dp`다.
14. TalkBack, font scale `1.3/1.5`, 대비 기준 점검을 MVP 핵심 화면에 바로 적용한다.
15. Figma 컴포넌트 이름과 코드 컴포넌트 이름을 1:1로 맞춘다.
