## 0. 전체 작업 흐름

구현은 아래 순서로 진행한다.

```text
문서 기준 확정
  ↓
DB/ERD 반영
  ↓
GraphHopper DB export/import pipeline
  ↓
GraphHopper 접근성 profile/custom model
  ↓
Backend 공통 기반과 외부 client
  ↓
도보 경로 API
  ↓
대중교통 경로 API
  ↓
select / transit-refresh / reroute / route-ratings
  ↓
Golden case 검증
  ↓
dev/prod 배포 pipeline 연결
```

작업 원칙:

- 구현 기준은 `.ai/PLANS/DOCS/Graphhopper_pipeline.md`, `Docs/ERD/ERD_v4.md`, `.ai/PLANS/DOCS/경로_API.md`, `.ai/PLANS/DOCS/보행기준.md`를 우선한다.
- 백엔드 코드는 반드시 `Docs/skills/backend/backend-convention.md`, `Docs/skills/backend/layer-package-convention.md`, `Docs/skills/backend/api-response-error-convention.md`, `Docs/skills/backend/config-external-convention.md`를 읽고 작성한다.
- 경로 API 구현은 `BE/src/main/java/com/ssafy/e102/domain/route` 도메인 폴더 안에 둔다.
- `domain/route` 구조는 현재 구현된 `BE/src/main/java/com/ssafy/e102/domain/user`의 `controller`, `dto/request`, `dto/response`, `entity`, `exception`, `repository`, `service`, `type` 패턴을 기준으로 맞춘다.
- 서비스 레포에서는 PoC 문서의 `graphhopper/...` 경로를 `INF/graphhopper/...`로 매핑한다.
- API 명세에 없는 FE 응답 필드와 enum은 추가하지 않는다.
- 외부 API key, 사용자 토큰, 개인정보는 로그에 남기지 않는다.
- 각 브랜치는 작은 단위로 끝내고, 성공 기준을 만족한 뒤 다음 브랜치로 넘어간다.
- 브랜치명은 지라 숫자 이슈번호를 suffix로 붙인다. BE 작업은 `be/feat/{설명}-{이슈번호}` 또는 `be/fix/{설명}-{이슈번호}`를 사용한다.
- 커밋 메시지는 타입별 gitmoji와 Jira 전체 키를 함께 포함한다. 예: `✨ Feat[S14P31E102-271]: GraphHopper 설정 추가`
- 구현 커밋이 끝나면 결과를 `.ai/PLANS/DOCS/REVIEW/`에 `YYYY-MM-DD_{이슈번호}_{요약}_review.md` 형식으로 기록한다. 구현 범위, 변경 파일, 검증 결과, 남은 주의사항을 포함한다.
- 구현이 완료된 작업은 같은 턴에서 관련 구현 계획 문서의 체크리스트를 `[x]`로 갱신한다. 실제 실행 검증을 하지 않은 성공 기준은 구현 코드가 있어도 체크하지 않고, 미실행 사유를 REVIEW 문서나 응답에 남긴다.
- 구현 코드는 불필요하게 모든 줄마다 주석을 달지 않는다. 대신 클래스 단위로 이 클래스의 책임, 입력/출력, 호출되는 주요 협력 객체를 이해할 수 있게 주석 또는 JavaDoc을 남긴다.
- 클래스 내부에서도 DB 적재, geometry 변환, 외부 API 호출, GraphHopper export/build, route ranking, reroute 판단처럼 흐름을 따라가기 어려운 주요 코드에는 어떤 역할을 하고 다음에 어디를 호출하는지 짧은 주석을 남긴다.
- 단순 getter/setter, 명확한 DTO mapping, enum 선언처럼 코드 자체로 의미가 분명한 부분에는 반복 설명 주석을 붙이지 않는다.

### 1.1 Backend route API 패키지 기준

경로 API는 `경로_API.md`의 path, request, response, error를 그대로 구현하되, 코드는 `domain` 하위의 `route` 도메인 폴더에 둔다.

```text
BE/src/main/java/com/ssafy/e102/domain/route
├─ controller
│  └─ RouteController.java
├─ dto
│  ├─ request
│  └─ response
├─ entity
├─ exception
│  ├─ RouteErrorCode.java
│  └─ RouteException.java
├─ repository
├─ service
└─ type
```

구현 시 현재 `domain/user` 코드 구조를 우선 참고한다.

- Controller는 `@RequestMapping("/routes")` 또는 `@RequestMapping("/route-ratings")`를 사용하고, 기본 `/api` prefix를 붙이지 않는다.
- 인증 사용자는 `@AuthenticationPrincipal AuthPrincipal principal`로 받는다.
- 성공 응답은 `global.response.ApiResponse`로 감싼다.
- Request DTO는 `dto/request`, Response DTO는 `dto/response`에 둔다.
- 도메인 에러 코드는 `domain.route.exception.RouteErrorCode`가 `global.exception.ErrorCode`를 구현하는 방식으로 둔다.
- 도메인 예외는 `RouteException extends BusinessException` 형태로 둔다.
- Entity, Repository, Service, type enum은 `domain/user`의 패키지 분리와 네이밍 패턴을 따른다.
- 외부 API client는 도메인 패키지에 넣지 않고 `global.external.graphhopper`, `global.external.odsay`, `global.external.bims`에 둔다.
- `publictransit` 도메인은 기존 대중교통 데이터/엔티티와 협력하는 영역으로 두고, `경로_API.md`의 `/routes/**`, `/route-ratings` Controller와 주요 orchestration Service는 `domain/route`에 둔다.

## 4. Branch 1: 티켓별 DB schema 선행 작업

목표: `ERD_v4.md` 기준으로 DB schema, entity, repository를 먼저 안정화한다. MVP 초기 dev 단계에서는 별도 schema SQL/Flyway migration이 아니라 JPA `ddl-auto=update`로 dev DB 테이블/컬럼을 생성한다. 별도 schema SQL 또는 Flyway migration은 schema가 안정된 뒤 도입한다.

주요 작업:

- `road_nodes`, `road_segments`, `segment_features` 구조 확인
- `road_segments` 접근성 컬럼 반영
- `route_sessions` 추가
- `route_ratings` 추가 또는 수정
- `subway_station_elevators.odsayStationId` 추가
- Redis key는 DB schema가 아니라 구현 문서에만 둔다.

작업 체크리스트:

- [ ] dev 환경은 `JPA_DDL_AUTO=update`로 JPA entity 기반 테이블/컬럼 생성을 허용한다.
- [ ] prod 또는 안정화 단계는 `JPA_DDL_AUTO=validate`로 전환한다.
- [ ] PostGIS extension 생성과 대량 CSV 적재는 JPA가 아니라 SQL/psql로 처리한다.
- [ ] Spring Boot JPA/Hibernate가 DB 컬럼명을 `camelCase`로 유지하도록 설정하거나 Entity에 `@Column`, `@JoinColumn` 이름을 명시한다.
- [ ] `road_nodes."vertexId"`, `road_segments."edgeId"`처럼 GraphHopper/CSV/SQL이 참조하는 quoted camelCase 컬럼명이 실제 DB에 생성되는지 확인한다.
- [ ] JPA entity에 `road_segments.walkAccess`를 `YES`, `NO`, `UNKNOWN` 기준으로 반영
- [ ] `slopeState`: `FLAT`, `MODERATE`, `STEEP`, `RISK`, `UNKNOWN`
- [ ] `widthState`: `ADEQUATE_150`, `ADEQUATE_120`, `NARROW`, `UNKNOWN`
- [ ] `surfaceState`: `VARCHAR(30)`, 값 후보 `PAVED`, `UNPAVED`, `UNKNOWN`
- [ ] `signalState`: `YES`, `NO`, `UNKNOWN`
- [ ] `segmentType`: `CROSS_WALK`, `SIDE_LINE`
- [ ] `segmentType`에 `UNKNOWN`을 추가하지 않음
- [ ] `crossingState` 컬럼을 만들지 않고 `segmentType + signalState` 파생 규칙으로 처리
- [ ] `route_sessions.routeId`를 `VARCHAR(120)`로 반영
- [ ] `route_sessions.routeSnapshotJson`을 `JSONB NOT NULL`로 반영
- [ ] `route_sessions.status`: `ACTIVE`, `COMPLETED` 중심으로 반영
- [ ] `route_ratings.routeId`를 `VARCHAR(120)`로 반영
- [ ] `route_ratings.routeContextJson`을 `JSONB NULL`로 반영
- [ ] `route_ratings`에 `UNIQUE(userId, routeId)` 추가
- [ ] `route_ratings`에서 `routeOption`, `startPoint`, `endPoint`를 만들지 않음
- [ ] `subway_station_elevators.odsayStationId VARCHAR(30) NULL` 추가
- [ ] `INDEX(odsayStationId)` 추가
- [ ] `segment_features.featureType`, `geom`, `state`, `valueNumber`를 ERD 기준으로 반영한다.
- [ ] `segment_features`는 최종 라우팅 비용의 직접 기준이 아니라 feature 위치 기반 segment 분할, 검수, 지도 표시용 원천 feature로 사용한다.
- [ ] 하나의 원천 segment가 여러 feature 위치를 가지면 ETL 단계에서 feature geometry 경계 기준으로 여러 최종 `road_segments`로 나눌 수 있게 설계한다.
- [ ] JPA entity는 `BaseEntity`와 JPA Auditing 컨벤션을 따른다.
- [ ] API DTO에 Geometry 타입을 직접 노출하지 않는다.

성공 기준:

- [ ] dev DB에서 JPA `ddl-auto=update`로 필요한 테이블/컬럼이 생성된다.
- [ ] JPA entity/repository 로딩 테스트가 성공한다.
- [ ] `route_sessions`, `route_ratings`, `subway_station_elevators` 컬럼이 ERD와 일치한다.
- [ ] `road_segments` enum/값 후보가 `Graphhopper_pipeline.md`와 일치한다.

### 5.1 dev DB road network CSV 적재 계획

목표: 클라우드 dev DB에 JPA로 생성된 `road_nodes`, `road_segments` 테이블을 기준으로 로컬 CSV를 대량 적재한다.

입력 파일:

- `.ai/LOCAL/nodes.csv`
- `.ai/LOCAL/segments.csv`

현재 CSV 정합성:

- `nodes.csv` 컬럼은 `vertexId`, `sourceNodeKey`, `point`이며 `road_nodes` Entity와 일치한다.
- `segments.csv` 컬럼은 `edgeId`, `fromNodeId`, `toNodeId`, `geom`, `lengthMeter`, `walkAccess`, `avgSlopePercent`, `widthMeter`, `brailleBlockState`, `audioSignalState`, `slopeState`, `widthState`, `surfaceState`, `stairsState`, `signalState`, `segmentType`이며 `road_segments` Entity와 일치한다.
- `segments.csv.segmentType`은 구현 enum에 맞춰 `SIDE_LINE`, `CROSS_WALK`만 사용한다.
- `avgSlopePercent`는 전부 빈 값일 수 있고, `widthMeter`도 일부 빈 값일 수 있으므로 적재 시 빈 문자열을 `NULL`로 처리한다.
- CSV 파일은 `.ai/LOCAL/` 하위 로컬 파일이므로 커밋 대상에 포함하지 않는다.

적재 방식:

- dev DB 접속 준비는 인프라 안내에 따라 `make be-dev-up`을 사용한다.
- 작업 종료 후 `make be-dev-down`으로 연결을 정리한다.
- PostGIS extension 생성은 JPA가 아니라 SQL로 선행한다.
- JPA `ddl-auto=update`로 `road_nodes`, `road_segments` 테이블과 camelCase 컬럼이 생성된 것을 확인한 뒤 적재한다.
- 대량 적재는 JPA repository 반복 save가 아니라 `psql \copy` 또는 `COPY` 기반으로 수행한다.
- geometry 컬럼은 CSV의 `SRID=4326;POINT(...)`, `SRID=4326;LINESTRING(...)` 값을 `ST_GeomFromEWKT()`로 변환해 넣는다.
- 안전한 적재를 위해 임시 staging table에 먼저 `text`로 적재한 뒤, 검증을 통과하면 본 테이블에 insert한다.
- 재실행 가능하도록 본 적재 전에 dev DB의 대상 범위를 `TRUNCATE road_segments, road_nodes` 또는 `ON CONFLICT` 정책 중 하나로 명확히 선택한다. MVP 초기 전체 교체 적재는 `TRUNCATE + INSERT`를 기본으로 한다.
- FK를 코드에 아직 만들지 않았더라도 적재 검증에서 `segments.fromNodeId`, `segments.toNodeId`가 `nodes.vertexId`에 모두 존재하는지 확인한다.

적재 전 검증:

- `nodes.csv` 필수 컬럼 누락 없음
- `segments.csv` 필수 컬럼 누락 없음
- `nodes.vertexId` 중복 없음
- `nodes.sourceNodeKey` 중복 없음
- `segments.edgeId` 중복 없음
- `segments.fromNodeId`, `segments.toNodeId`가 모두 nodes에 존재
- `point`는 `SRID=4326;POINT(...)` 형식
- `geom`은 `SRID=4326;LINESTRING(...)` 형식
- enum 값은 Entity enum 후보와 일치

적재 후 검증:

- `SELECT COUNT(*) FROM road_nodes;` 결과가 `nodes.csv` 데이터 row 수와 일치한다.
- `SELECT COUNT(*) FROM road_segments;` 결과가 `segments.csv` 데이터 row 수와 일치한다.
