## 1. 프로젝트 문서 기반 해석 요약

### 1.1 범위 해석

- 공식 MVP는 Android 11개 화면 중심이다.
  - 근거: `2026-04-11_MVP_화면명세서.md`
- 로그인, 회원가입, 설정, 제보내역, 시각장애 전용 UI, 음성검색, 재탐색, 저상버스, 두리발은 비MVP다.
  - 근거: `2026-04-10 최종_프로젝트_기획서.md` 4.2, `2026-04-11_확장_기능_화면명세서.md`
- 하지만 PRD의 발표 KPI는 아래 3개 시나리오를 end-to-end 시연 가능 상태로 요구한다.
  - 전동휠체어 경로 안내
  - 시각장애인 음성 목적지 탐색
  - 도로 상태 제보
  - 근거: `2026-04-09_부산이음길_PRD.md` 8장

### 1.2 일정 해석

- `5/3`까지는 비로그인 중심 MVP를 닫아야 한다.
- `5/11 ~ 5/20`은 발표용 보강 기간으로 분리해야 한다.
- 시각장애 시연은 정식 full 기능 구현이 아니라 발표형 보강 범위로 내려야 한다.
  - 근거: MVP/비MVP 문서 충돌과 발표 KPI 간 불일치

### 1.3 핵심 문서 충돌

| 충돌 항목 | 문서 근거 | 일정 판단 |
|---|---|---|
| 비로그인 MVP 원칙 vs 북마크/자주 가는 길/제보 API 인증 필수 | PRD, 기획서 8장 vs API 명세 | local-first로 선구현, 서버 sync는 후행 |
| 점자블록은 필수 기능인데 전용 API/데이터 없음 | PRD 3.2.3, 기능명세서 2-3 | demo area static seed로 임시 대응 |
| 시설 상세에 운영시간 표기 vs 장소 상세 API는 운영시간 저장 안 함 | MVP 화면명세서 SCR-007 vs 장소 상세 API 비고 | 운영시간은 optional 처리 또는 숨김 |
| 경로 수집은 필수 기능 vs 업로드 API HOLD | 기능명세서 5-1 vs API 전체 목록 HOLD | 로컬 session log까지만 구현 |
| 시각장애 음성 탐색은 발표 핵심 KPI vs 비MVP 분류 | PRD KPI vs 확장 화면명세서 | 발표 보강 범위로 재배치 |

### 1.4 인터뷰 기반 제품 우선순위

- 최단거리보다 안전성과 실제 통행 가능성이 우선이다.
- 위험 요소는 사전 노출되어야 한다.
- 화장실, 충전기, 진입 가능 여부 같은 접근성 정보가 함께 보여야 실사용성이 올라간다.
- 음성 기능은 단독 수단이 아니라 화면 보조 수단으로 다뤄야 한다.
  - 근거: `2026-04-10_함세상_장애인자립생활센터_인터뷰_결과.md`

따라서 프론트는 `SAFE 경로`, `위험도 표시`, `시설 접근성 정보`, `offline demo 안정성`을 우선해야 한다.

## 5. 로컬 저장 vs 로그인 연동 분기 전략

### 5.1 기본 원칙

- 화면은 인증 상태를 직접 보지 않는다.
- 모든 저장 기능은 `Unified Repository` 뒤에 숨긴다.
- 기본 저장소는 `Room + DataStore`다.
- 로그인은 후속 `RemoteSyncAdapter`로 붙인다.

### 5.2 도메인별 전략

| 도메인 | 비로그인 기본 | 로그인 후 | 일정 판단 |
|---|---|---|---|
| 온보딩/약관/설정 | DataStore | 서버 settings sync optional | local 우선 |
| 북마크 | Room | sync adapter로 서버 반영 | local 먼저 완료 |
| 자주 가는 길 | Room | sync adapter로 서버 반영 | local 먼저 완료 |
| 제보 draft/outbox | Room | 성공 시 서버 전송 | auth 없으면 outbox 유지 |
| 경로수집 로그 | Room/file | 업로드 API 생기면 전송 | 현 단계 local만 |

### 5.3 구현 규칙

- API 완성 대기 금지
- 서버 연동 실패 시 UI 기능 자체는 유지
- local 데이터 삭제 정책은 명확히 분리
  - 앱 삭제 시 손실 허용
  - 로그아웃은 local 데이터 유지
    - 근거: PRD 3.1.3
