# Debugging Memory

## Purpose

Capture recurring investigation patterns, sharp reproductions, and failure signatures that future sessions should not rediscover from scratch.

## Entry format

- Date
- Symptom
- Root cause
- Fastest reproduction path
- Durable fix
- Regression test or alert that should exist

## 2026-05-07

- Symptom: `POST /auth/social-login` returns HTTP 500 in both frontend social login flow and `auth-test.html`.
- Root cause: the `User` JPA entity uses camelCase property names without explicit snake_case `@Column(name=...)` mappings while Spring/Hibernate is configured with `PhysicalNamingStrategyStandardImpl`. Hibernate generated SQL against `users.userId`, `users.socialProvider`, `users.socialProviderUserId`, which PostgreSQL resolves to lowercase `userid`, `socialprovider`, `socialprovideruserid`. The actual dev table uses snake_case columns such as `user_id`, `social_provider`, `social_provider_user_id`, so the repository lookup fails before login or signup can proceed.
- Fastest reproduction path: trigger social login once on dev, then inspect `s14p31e102-dev-backend-1` logs for `column u1_0.userid does not exist` and compare with `psql \\d+ users` on dev DB.
- Durable fix: align entity mappings and schema naming. Prefer explicit `@Column(name = \"snake_case\")` and `@UniqueConstraint(columnNames = {...})` values that match the actual schema, then keep dev/prod on schema validation rather than relying on `ddl-auto:update` to mutate drifted tables.
- Regression test or alert that should exist: integration test for `AuthService.socialLogin` against a real Postgres schema with snake_case columns, plus startup validation or migration checks that fail if JPA mapping and DB naming diverge.

## 2026-05-08

- Symptom: `e102-prod-deploy` fails in two ways on S2: `scp ... .env.prod: Permission denied` during upload or `scripts/deploy/prod-smoke.sh: Permission denied` during remote deploy, and Jenkins boolean parameters such as `BUILD_GRAPHHOPPER` appear blank in shell logs even when the pipeline defines them.
- Root cause: prod secret upload wrote directly to an existing `.env.prod`, so a root-owned target file blocked overwrite even though the directory itself was writable. Separately, files delivered via `git archive` do not guarantee executable mode on S2 for deployment scripts, so direct script execution depends on a brittle remote permission state. In the Jenkinsfile, boolean params were interpolated inside raw `sh` as shell variables instead of being passed from `params.*`, so the shell saw empty strings.
- Fastest reproduction path: trigger `e102-prod-deploy` on `master`, inspect Jenkins `Upload To S2` for `.env.prod` overwrite failure, or inspect `Deploy Or Rollback` for `prod-smoke.sh: Permission denied` and blank `BUILD_GRAPHHOPPER=` / `DEPLOY_GRAPHHOPPER=` in the echoed remote command.
- Durable fix: upload `.env.prod` to a temp file and rename on S2, apply `chmod +x scripts/deploy/*.sh` immediately after extracting the workspace, invoke nested deploy scripts via `bash`, and construct remote commands from `params.ROLLBACK`, `params.BUILD_GRAPHHOPPER`, and `params.DEPLOY_GRAPHHOPPER` in Groovy before entering `sh`. Also fail fast if required secrets such as `JWT_SECRET` are absent from `.env.prod`.
- Regression test or alert that should exist: static regression tests for the Jenkinsfile upload pattern and `bash`-based nested script invocation, plus a prod deploy preflight that checks required env keys before building images.

- Symptom: `e102-dev-deploy` rebuilds GraphHopper cache and fails with `invalid_segment_geometry: segment geometry must be LINESTRING with at least two valid points` even though `road_segments.geom` rows pass PostGIS validity checks.
- Root cause: the invalid rows were synthetic child segments generated by `apply_segment_features_to_export`. On some edges, `CROSSWALK` and `BRAILLE_BLOCK` point features projected to extremely close fractions on the same source segment. The child segment between those fractions was still non-zero in floating point, but exporter serialization rounded coordinates to 8 decimal places, collapsing start and end into the same coordinate and making validation fail.
- Fastest reproduction path: run `export-postgis-to-osm.py --report-json ...` in the dev `graphhopper-build` container and inspect blocker samples such as synthetic edge `-27`; then trace its `source_edge_id` and compare nearby feature fractions.
- Durable fix: serialize GraphHopper export geometry and OSM node coordinates with higher precision so close split boundaries survive round-tripping, and keep validation on the serialized geometry.
- Regression test or alert that should exist: unit test with two nearly overlapping point features on one source edge that previously collapsed to the same 8-decimal coordinate after splitting.
