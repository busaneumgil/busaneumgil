# 2026-05-12 제보 탭 실제 데이터 연동 구현계획

## 1. 문서 목적

- 제보 탭(REPORT-01~04)에서 실제 데이터 연동이 되지 않고 mock/shell/placeholder 값으로 채워져 있는 영역을 코드 기준으로 식별한다.
- 각 영역에 대해 현재 사실, 영향, 구현 방향을 정리하고 우선순위를 부여한다.
- 본 문서는 FE lane 범위이며, 코드 수정은 별도 Task/Branch에서 진행한다. BE 협의가 필요한 항목은 §9에 분리한다.
- 선행 컨텍스트: `FE/docs/qa/2026-05-08_제보_작성_QA_체크리스트.md`, `FE/docs/qa/2026-05-08_제보_완료_재진입_QA_체크리스트.md`는 ViewModel 로직 기준으로 "마감" 선언했으나, 실제 UI 입력 수단 대부분이 mock인 상태로 시연에서 동작하지 않음.

## 2. 범위

- 포함 범위
  - 제보 작성 4단계(REPORT-01 유형 → REPORT-02 위치 → REPORT-03 사진/설명 → REPORT-04 완료) UI 입력 수단 실연동

  - ViewModel이 emit하지만 Route에서 무시되는 UI 이벤트 연결
  - 서버 제출 페이로드 정합성(특히 `imageUrls`)
- 제외 범위
  - BE 신규 API 설계 (이미지 업로드, 멱등성 키 등은 §9에 협의 사항으로만 기록)

## 4. 실제로 연동되어 동작하는 영역 (참고)

mock이 아니라 실제 데이터로 정상 동작하는 영역. 작업 시 회귀를 피해야 할 대상.

- Room DB draft 저장/조회/삭제 — `ReportDraftDao`, `ReportRepository.saveDraft` (라인 180-197)
- Room DB outbox 저장 — `ReportOutboxDao`, `ReportRepository.saveOutbox` (라인 199-212)
- `POST /hazard-reports` 서버 제출 — `ReportRepository.submitOutboxToServer` (라인 214-265)
- 토큰 인증 — `accessTokenProvider` 주입 (라인 140)
- 멱등 재시도 — 이미 `Submitted`인 outbox는 새 호출 안 함 (라인 221-226)
- `GET /hazard-reports/me` 내역 조회 + 로컬 outbox merge — 라인 293-322
- `GET /hazard-reports/me/{id}` 상세 조회 — 라인 324-330
- draft → form 복원 step 자동 점프 — `toUiState()` 라인 659-664
- 4단계 step 전환 / 뒤로가기 / `TabReentered` 정책 — ViewModel
- 입력 validation (좌표 범위, 설명 300자, 사진 5장 cap) — `validateLocation`, `validateDescription`, `validatePhotos`

### 5.3 [우선순위 3] 현재 위치 — CurrentLocationManager 연결

- 목표: "현재 위치로 설정" 버튼이 실제 디바이스 GPS 좌표를 가져온다.
- 작업 범위
  - `ReportViewModel`에 `CurrentLocationManager` 주입 (`ReportViewModel.provideFactory`에 파라미터 추가)
  - `setCurrentLocationShell()` 삭제 → `requestCurrentLocation()`로 교체

  - 권한 거부 시 `ReportLocationError.PermissionDenied`, 위치 fetch 실패 시 `CurrentLocationUnavailable` (enum은 이미 `ReportContract.kt:299-303`에 정의됨)

- 완료 기준: 실제 디바이스 위치가 좌표/주소(가능하면)로 입력됨

- 의존성: 없음

- 의존성: 없음 (단, §5.6과 통합 필요)

### 5.6 [우선순위 6] 이미지 업로드 정책 결정 + `imageUrls` 실제 전송

- 목표: 첨부된 사진이 서버에 실제로 등록된다.
- 사전 결정 필요 (BE 협의)
  - 업로드 엔드포인트 — S3 presigned URL 발급 후 PUT? multipart로 직접 업로드?
  - 업로드 시점 — outbox 저장 시 즉시? 제출 직전?
  - 실패 시 정책 — 사진 업로드 실패해도 제보는 등록? 전체 롤백?
- FE 작업 범위 (BE 결정 후)
  - 업로드 API 호출 추가 (`HazardReportsRemoteDataSource` 확장 또는 별도 `ImageUploadRemoteDataSource`)
  - 업로드 결과 URL을 outbox에 보존
  - `submitOutboxToServer()`에서 `imageUrls = emptyList()`를 실제 URL 배열로 교체 (`ReportRepository.kt:242`)
- 완료 기준: 첨부 사진이 서버 응답 detail에서 imageUrls로 노출됨
- 예상 난이도: 높음
- 의존성: §5.5 + BE 협의

### 5.7 [우선순위 7] Draft 사진 5장 영속화 스키마 마이그레이션

- 목표: 5장 첨부 후 임시저장해도 5장 모두 복원된다.
- 작업 범위
  - 옵션 A: 별도 `report_draft_photos` 테이블 + `draftId` FK
  - 옵션 B: 단일 컬럼에 JSON 배열로 직렬화
  - 권장: 옵션 A — 향후 사진별 메타데이터 확장 여지
  - Room migration 추가 (스키마 버전 증가)
  - `ReportDraftEntity` 또는 새 `ReportDraftWithPhotos` 관계 도입
  - `toDraftData()`/`toUiState()`/`toEntity()` 사진 리스트 처리로 변경
- 완료 기준: 5장 첨부 → 임시저장 → 앱 재시작 → 이어하기 시 5장 모두 복원
- 예상 난이도: 중간
- 의존성: §5.5 (단일 사진 picker 완료 후 진행이 안전)

### 5.8 [우선순위 8] NetworkMonitor 실제 구현 + 오프라인 분기

- 목표: 오프라인 상태에서 사용자에게 사전 안내한다.
- 작업 범위
  - `ConnectivityManager` 기반 `AndroidNetworkMonitor` 구현
  - `AppContainer`에서 주입 (현재 `DefaultNetworkMonitor`는 dead code이므로 사용처 없음 — 새로 wiring 필요)
  - `ReportViewModel.submitReport()`에서 호출 전 `isOnline()` 체크 → 오프라인이면 outbox만 저장하고 "오프라인 상태입니다. 네트워크 복구 시 자동 재시도됩니다." 안내
  - 백그라운드 재시도는 별도 Task (WorkManager 등) — 본 작업에서는 사용자 명시 재시도까지만
- 완료 기준: 비행기 모드에서 제출 시도 시 명확한 사전 안내가 표시됨
- 예상 난이도: 낮음~중간
- 의존성: §5.2 (Snackbar 연결 선행 권장)

### 5.9 [우선순위 9] Submitting outbox cleanup + 401 자동 재로그인

- 작업 범위 (2개 묶음)
  - 앱 시작 시 `status=Submitting`인 outbox를 `Pending`으로 복구 (`AppContainer` init 또는 별도 startup job)
  - 401 응답 시 로그인 화면으로 자동 navigate 옵션 — 인증 도메인과 cross-cutting이므로 별도 협의 필요
- 예상 난이도: 낮음 (cleanup) / 중간 (401 흐름은 도메인 외부 영향)
- 의존성: 401 부분은 인증 도메인 담당자와 협의

### 5.10 [우선순위 10] 서버 list 응답의 description/address 표시

- 옵션 A: BE에 list 응답 확장 요청 (description, address 포함)
- 옵션 B: FE에서 list 진입 시 각 항목의 상세를 자동 prefetch (네트워크 비용 부담)
- 권장: 옵션 A → §9에 협의 사항으로 기록
- 예상 난이도: BE 작업

## 8. 알려진 한계 (본 문서 범위 외)

- 사진 5장 첨부 시 BE 정책: 현재 명세상 imageUrls는 N개 허용으로 보이나, §5.6 협의 시 cap 재확인 필요
- 멱등성 키: 재시도 시 같은 outboxId 재사용하지만 BE 멱등성 보장 없음. 네트워크 race 시 중복 등록 가능 (§9)
- 저시력 모드 제보 흐름: 본 문서는 일반 모드 기준. 저시력 전용 화면 변형은 별도 Task

## 9. 백엔드 개발자에게 전달할 작업사항

| --- | --- | --- |
