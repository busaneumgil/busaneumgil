## 2. STT 텍스트 의미 분석

| 항목 | 내용 |
| --- | --- |
| 우선순위 | P1 |
| Method | `POST` |
| URL | `/voice/analyze` |
| 인증 | 불필요 |
| 설명 | FE가 STT로 변환한 텍스트를 AI 서버가 분석해 의도와 장소명을 추출한다. 이 API는 장소 검색을 직접 수행하지 않으며, 장소명이 확정되면 FE가 `GET /places/search`를 별도로 호출한다. |

### Request

#### Header

| 이름 | 필수 | 설명 |
| --- | --- | --- |
| Content-Type | Y | `application/json` |

#### Body

| 필드명 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| text | string | Y | STT 변환 텍스트 |
| mode | string | Y | 사용자 흐름. `MOBILITY_IMPAIRED`, `LOW_VISION` |
| history | array | N | 이전 대화 목록. `LOW_VISION` 전용. 기본값 `[]`. `MOBILITY_IMPAIRED`에서는 무시 |
| history[].role | string | Y | 발화 주체. `user`, `assistant` |
| history[].content | string | Y | 발화 내용. `assistant`의 경우 이전 응답 `data`를 JSON 문자열로 직렬화한 값 |

#### Request Example - 보행약자

```json
{
  "text": "마 이재모피자 어디있는지 알려주소",
  "mode": "MOBILITY_IMPAIRED"
}
```

#### Request Example - 저시력자 1턴

```json
{
  "text": "이재모피자 어디야",
  "mode": "LOW_VISION",
  "history": []
}
```

#### Request Example - 저시력자 2턴 긍정 응답

```json
{
  "text": "응",
  "mode": "LOW_VISION",
  "history": [
    {
      "role": "user",
      "content": "이재모피자 어디야"
    },
    {
      "role": "assistant",
      "content": "{\"intent\":\"PLACE_SEARCH\",\"placeName\":\"이재모피자\",\"confirmed\":null,\"confirmationMessage\":\"이재모피자를 찾으시나요?\"}"
    }
  ]
}
```

#### Request Example - 저시력자 2턴 부정 후 새 장소

```json
{
  "text": "아니 부산대학교",
  "mode": "LOW_VISION",
  "history": [
    {
      "role": "user",
      "content": "부산역 어디야"
    },
    {
      "role": "assistant",
      "content": "{\"intent\":\"PLACE_SEARCH\",\"placeName\":\"부산역\",\"confirmed\":null,\"confirmationMessage\":\"부산역을 찾으시나요?\"}"
    }
  ]
}
```

### Response

- HTTP Status: `200 OK`

#### Data Fields

| 필드명 | 타입 | Null 가능 | 설명 |
| --- | --- | --- | --- |
| intent | string | N | 추론된 의도. `PLACE_SEARCH`, `UNKNOWN` |
| placeName | string | Y | 추출된 장소명. `intent=UNKNOWN`이면 `null` |
| confirmed | boolean | Y | 저시력자 전용 확인 상태. `true`는 확인 완료, `false`는 부정 또는 판단 불가, `null`은 아직 확인 전 상태. `MOBILITY_IMPAIRED`는 항상 `null` |
| confirmationMessage | string | Y | 저시력자 전용 TTS 문구. 확인 질문 또는 재입력 안내가 필요할 때 값이 있음. `MOBILITY_IMPAIRED`는 항상 `null` |

#### Success Example - 보행약자 장소 검색

```json
{
  "status": "S2000",
  "data": {
    "intent": "PLACE_SEARCH",
    "placeName": "이재모피자",
    "confirmed": null,
    "confirmationMessage": null
  },
  "message": "정상 처리되었습니다."
}
```

#### Success Example - 보행약자 의도 미확인

```json

    "confirmed": null,

}
```

#### Success Example - 저시력자 1턴 장소 확인 요청

### Error

| HTTP Status | status | message | 발생 조건 |
| --- | --- | --- | --- |
| 400 | V4000 | 음성 분석 요청값이 올바르지 않습니다. | `text` 누락/빈 문자열, `mode` 누락/후보값 오류, `history` 형식 오류 |
| 502 | V5020 | 음성 분석 AI 호출에 실패했습니다. | AI 서버 호출 실패 또는 LLM 추론 실패 |

#### Error Example

```json
{
  "status": "V4000",
  "message": "음성 분석 요청값이 올바르지 않습니다."
}
```

## 3. FE/BE/AI 연동 흐름

### 보행약자

```text
1. FE가 음성을 텍스트로 변환한다.
   예: "마 이재모피자 어디있는지 알려주소"

2. FE가 BE에 음성 분석을 요청한다.
   POST /voice/analyze
   mode = MOBILITY_IMPAIRED

3. BE가 AI 서버에 분석 요청을 보낸다.

4. AI는 문장에서 장소명을 추출한다.
   예: "이재모피자"

5. BE는 AI 응답을 공통 응답 형식으로 변환해 FE에 내려준다.

6. FE는 추출된 장소명으로 바로 장소 검색을 요청한다.
   GET /places/search?keyword=이재모피자&lat=...&lng=...

7. BE는 카카오 장소 검색 API를 호출한다.

8. 카카오는 장소 후보를 반환한다.
   - kakaoPlaceId
   - 장소명
   - 주소
   - 좌표
   - 카카오 카테고리

9. BE는 카카오 장소 ID를 기준으로 우리 places.providerPlaceId와 매칭한다.

10. 우리 DB에 매칭되는 장소가 있으면 내부 placeId, serviceCategory, accessibilityFeatures, matched=true를 함께 내려준다.

11. 우리 DB에 매칭되는 장소가 없으면 카카오 장소 정보만 내려주고 placeId=null, serviceCategory=null, accessibilityFeatures=[], matched=false로 응답한다.
```

### 저시력자

```text
1. FE가 음성을 텍스트로 변환한다.
   예: "이재모피자 어디야"

2. FE가 BE에 음성 분석을 요청한다.
   POST /voice/analyze
   mode = LOW_VISION
   history = []

3. BE가 AI 서버에 분석 요청을 보낸다.

4. AI는 문장에서 장소명을 추출하고 확인 문장을 만든다.
   예: "이재모피자를 찾으시나요?"

5. BE는 AI 응답을 공통 응답 형식으로 변환해 FE에 내려준다.
   confirmed = null

6. FE는 confirmationMessage를 TTS로 재생한다.

7. FE는 다시 음성을 입력받는다.
   예: "응"

8. FE가 BE에 두 번째 음성 분석을 요청한다.
   POST /voice/analyze
   mode = LOW_VISION
   history = 이전 대화 목록

9. AI는 사용자가 이전 장소명을 확인했는지 판단한다.
   confirmed = true

10. BE는 AI 응답을 FE에 내려준다.

11. FE는 confirmed=true일 때 장소 검색을 요청한다.
    GET /places/search?keyword=이재모피자&lat=...&lng=...

12. 이후 카카오 장소 검색과 우리 DB 접근성 정보 매칭 흐름은 보행약자와 동일하다.
```

### 저시력자 부정 응답

```text
사용자: "부산역 어디야"
AI: "부산역을 찾으시나요?"
사용자: "아니 부산대학교"

응답:
intent = PLACE_SEARCH
placeName = 부산대학교
confirmed = null
confirmationMessage = "부산대학교를 찾으시나요?"

이 경우 FE는 아직 /places/search를 호출하지 않고, 다시 TTS 확인 후 confirmed=true가 되면 검색한다.
```

## 4. 책임 분리

| 주체 | 책임 |
| --- | --- |
| FE | 마이크 권한 요청, STT 실행, 저시력자 대화 히스토리 관리, TTS 재생, 장소명 확정 후 `/places/search` 호출 |
| BE | `/voice/analyze` 제공, AI 서버 호출, AI 응답 검증/공통 응답 변환, `/places/search` 제공 |
| AI | STT 텍스트에서 의도와 장소명 추출, 저시력자 확인 문장 생성, 확인 응답 판단 |
| Kakao | 실제 장소 검색 원천 |
| 우리 DB | `places.providerPlaceId` 기준 매칭, 서비스 카테고리와 접근성 정보 보강 |

| 원칙 | 내용 |
| --- | --- |
| 음성 분석 | `/voice/analyze`는 장소 검색을 수행하지 않는다. |
| 장소 검색 | `/places/search`는 자연어 문장을 해석하지 않고 확정된 검색어만 검색한다. |
| DB 저장 | `places`는 카카오 검색 결과 전체를 저장하지 않고, 접근성 정보가 있는 우리 서비스 장소를 관리한다. |
| 매칭 키 | 카카오 장소 ID는 `places.providerPlaceId`와 매칭한다. |
