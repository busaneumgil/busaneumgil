## Problem List

- 문제 1: `MapViewport`가 실제 SDK가 아니라 fallback surface만 렌더링한다.
- 문제 2: `MapViewModel`의 marker/detail source가 `FacilitySeedRepository`에 고정돼 있다.
- 문제 3: `PlacesRemoteDataSource`, `SearchRemoteDataSource`가 TODO 상태라 production place flow가 닫히지 않는다.
- 문제 4: 현재 FE marker category 모델과 실제 API의 `category` / `featureType` 분리 계약이 어긋난다.
- 문제 5: `/places/search`의 `matched=false`, `placeId=null` 계약이 현재 `SearchResult` / bookmark UX와 직접 맞지 않는다.

## Architecture And Data Flow

- 유지할 상위 흐름:
  - `MapViewModel -> MapUiState -> MapScreen -> MapViewport`
  - `marker tap -> facility detail sheet -> PlaceDestination -> DestinationSelectionRepository`
- SDK 연동 경계:
  - SDK 객체는 `MapViewport` 내부 adapter에서만 관리
  - ViewModel/Contract에는 SDK 타입 비노출
- 데이터 흐름:
  - 지도 browse: `GET /places` -> remote datasource -> repository -> map mapper -> `markerOverlayState`
  - 시설 상세: `GET /places/{placeId}` -> repository -> `facilityDetailSheetState`
  - 검색: `GET /places/search` -> `SearchRepository` -> `SearchViewModel` -> `PlaceDestination`
- fallback 정책:
  - production read path는 `remote -> local -> mock`
  - preview/test는 fallback surface와 mock data 유지

## 1. 현재 상태 요약

### current implementation fact

- 지도 렌더링은 아직 실제 SDK가 아니다.
  - `MapViewport`는 `MapIntegrationState.Unbound`일 때 fallback surface를 그리고, `Bound`여도 동일 fallback surface를 재사용한다.
- 지도 화면의 상위 상태 계약은 이미 분리되어 있다.
  - `MapUiState`는 `cameraTarget`, `markerOverlayState`, `facilityDetailSheetState`, `selectedMarkerId`, `selectedDestination`를 보유한다.
- 화면 오버레이 경계도 이미 분리되어 있다.
  - `MapScreen`은 `MapShellScaffold` 안에서 `MapViewport`, 상단 검색/필터, 우측 플로팅 버튼, 하단 시설 상세 또는 최근 목적지 시트를 별도 슬롯으로 조합한다.
- 마커/시설 데이터는 seed 기반이다.
  - `MapViewModel`은 `facilitySeedRepository.getFacilityBrowseData()`로 마커/상세/필터 상태를 구성한다.
  - 시설 선택 후 길안내 진입은 `FacilityDetailSeed -> PlaceDestination` handoff로 처리한다.
- 앱 컨테이너에는 실제 장소/검색 repository 골격이 이미 있다.
  - `AppContainer`는 `placesRepository`, `searchRepository`를 생성한다.
  - 하지만 `PlacesRemoteDataSource`, `SearchRemoteDataSource`는 둘 다 TODO stub 상태다.
- 검색 흐름은 구조만 준비되어 있다.
  - `SearchViewModel`은 `DestinationSelectionRepository`를 통해 목적지 handoff를 수행하고, 최근 목적지 저장 시 `placesRepository.getPlaceDetail()`에 의존한다.

### 구현상 드러난 핵심 불일치

- 현재 map seed category는 `TOILET`, `ELEVATOR`, `CHARGING_STATION` 같은 “지도 표시용 분류”까지 포함한다.
- 장소 API는 `category`와 `featureType`을 분리한다.
  - `category`: `FOOD_CAFE`, `TOURIST_SPOT`, `ACCOMMODATION`, `HEALTHCARE`, `WELFARE`, `PUBLIC_OFFICE`, `ETC`
  - `featureType`: `accessibleToilet`, `elevator`, `chargingStation` 등
- 즉, 현재 marker/filter 표현 모델은 seed 친화적이고, 실제 API 계약은 place category + accessibility feature 조합 기반이다.

## 2. 문서 기준 Target Contract 요약

### target contract

- `MAP-01`은 보행약자 공통 홈이며, 실제 지도 영역 위에 검색 진입, 필터, 위치 상태, 시설 선택 overlay를 얹는 구조를 유지한다.
- `FAC-01`은 별도 route가 아닌 `MAP-01` 내부 bottom sheet overlay다.
- Figma handoff 기준에서 실제 지도 SDK 연결 시 `MapViewport` 내부 렌더링만 교체하고, 외부 overlay 구조는 유지해야 한다.
- 장소 데이터 계약은 다음 순서를 따른다.
  - 지도 마커/목록: `GET /places`
  - 시설 상세: `GET /places/{placeId}`
  - 텍스트 검색: `GET /places/search`
  - 음성 의미 분석: `POST /voice/analyze`
- 목적지 handoff의 FE 표준 payload는 계속 `PlaceDestination`을 유지한다.
- 경로 API는 별도 도메인이며, 이번 작업에서는 지도 SDK 연동과 분리해서 본다.

### working basis for this task

- 지도 SDK 자체 연동은 `MapViewport` 교체에 집중한다.
- 지도 위 데이터 교체는 `FacilitySeedRepository` 직접 의존을 제거하고 실제 장소 API 소비 계층으로 바꾸는 데 집중한다.
- `MapUiState`, `cameraTarget`, `markerOverlayState`, `facilityDetailSheetState`, `PlaceDestination` handoff는 가능한 한 유지한다.

## 3. SDK 후보 비교와 추천

| 후보 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| Google Maps SDK | Compose 연동 자료가 가장 많고 공식 생태계가 안정적 | 국내 지도 디테일과 POI 맥락이 상대적으로 약함 | 이번 앱 도메인에는 우선순위 낮음 |
| Kakao Map SDK | 국내 POI 친화성은 강함 | FE는 직접 장소 검색을 하지 않고, Compose/AndroidView 패턴과 운영 레퍼런스 측면에서 실무 선택지가 다소 좁음 | 후보 가능하지만 1순위는 아님 |
| Naver Map SDK | 국내 지도 품질, Android 안정성, marker/polyline/camera 기능이 충분하고 지도 화면 대체 용도에 적합 | Compose 전용 API가 아니라 `AndroidView` 브리지가 필요 | 추천 |

### 추천 SDK

- 추천: `Naver Map SDK for Android`
- 추천 이유:
  - 이번 작업의 핵심은 “지도 엔진 교체”이지 “검색/POI 생태계 SDK 통합”이 아니다.
  - 실제 장소 검색은 이미 BE의 `/places`, `/places/search`가 책임지므로 FE는 지도 엔진의 렌더링 안정성과 국내 지도 품질을 우선하면 된다.
  - `MapViewport`를 `AndroidView(MapView)` 기반으로 감싸도 현재 overlay 구조를 그대로 유지하기 쉽다.

## 6. 선행 검토 사항

1. SDK 키/의존성
   - 현재 `FE/app/build.gradle.kts`에는 지도 SDK 의존성이 없다.
   - Naver Login 설정은 있으나 Naver Map SDK 설정은 별도 확인이 필요하다.
2. 지도 bridge 방식
   - `MapView`를 `AndroidView`로 감싸는 방식으로 갈지, `MapFragment`를 호스트하는 방식으로 갈지 결정해야 한다.
   - 현재 구조상 `MapViewport` 단일 컴포저블 교체를 위해 `AndroidView(MapView)`가 1순위다.
3. API-UI 매핑 규칙
   - `category`와 `featureType`을 어떤 marker visual rule로 합성할지 FE 내부 규칙이 필요하다.
4. unmatched search 결과 처리
   - `/places/search`는 `placeId=null`, `matched=false`가 가능하다.
   - 현재 `SearchResult.placeId: String` 계약과 북마크 저장 로직은 이 경우를 바로 표현하지 못한다.
5. 북마크 제약
   - 서버 북마크는 내부 `placeId`가 있는 장소만 저장 가능하다.
   - `matched=false` 결과의 bookmark UX 정책이 필요하다.
6. 접근성 문구 유지
   - fallback 안내 문구는 preview/개발 상태에만 남기고, 실제 지도 연결 시 TalkBack 라벨은 마커명 + 카테고리 + 선택 가능 상태로 재정의해야 한다.
7. 성능/쿼리 전략
   - `GET /places` 호출 기준 좌표, 반경, 재호출 임계값, debounce 기준을 FE에서 정해야 한다.

### 7.1 축 분리

#### A. 지도 SDK 자체 연동

- 목표: fallback surface를 실제 지도 엔진으로 교체하되 `MapViewport` 외부 계약은 유지한다.
- 핵심 산출:
  - provider-backed `MapViewport`
  - camera target sync
  - marker render / marker tap callback
  - 현재 위치 표시

#### B. 지도 위에 올릴 데이터 교체

- 목표: seed/mock marker/detail 흐름을 실제 장소 API 소비 구조로 교체한다.
- 핵심 산출:
  - `/places` marker browse
  - `/places/{placeId}` detail fetch
  - `/places/search` search result mapping
  - remote-local-mock fallback 정리

### 7.2 1단계: MAP-01 / FAC-01 실제 지도 SDK + 장소 마커/상세 연결

#### Step 1. SDK 도입 골격 추가

- `app/build.gradle.kts`에 Naver Map SDK 의존성 추가
- API key / manifest / runtime init 위치 확정
- Preview/test 빌드에서 SDK 초기화 없이도 fallback이 유지되도록 guard 추가

#### Step 2. `MapViewport`를 provider-backed container로 전환

- `MapViewportUiState`는 유지한다.
- `MapIntegrationState.Bound`일 때 실제 `NaverMap` renderer를 사용한다.
- `cameraTarget.requestId`를 camera 이동 트리거로 사용한다.
- marker 클릭은 기존 `onMarkerClick(markerId)` 콜백을 그대로 유지한다.
- fallback surface는 다음 용도로만 남긴다.
  - preview
  - test
  - SDK 초기화 실패 시 개발용 fallback

#### Step 3. 지도 렌더러 adapter 경계 만들기

- SDK 객체(`MapView`, `NaverMap`, `Marker`, `OverlayImage`, `CameraUpdate`)는 `feature/map/component` 내부에 가둔다.
- `MapViewModel`과 `MapContract`에는 SDK 타입을 노출하지 않는다.
- camera sync, marker diffing, lifecycle bind/unbind는 renderer adapter가 책임진다.

#### Step 4. `GET /places` 기반 map browse 계층 도입

- 기존 `FacilitySeedRepository` 의존 자리를 실제 장소 browse 계층으로 치환한다.
- 구현 방향:
  - `PlacesRemoteDataSource.getPlaces(query)` 실제 구현
  - 응답 DTO -> FE domain model mapper 작성
  - `MapViewModel`에는 “browse 결과”만 전달
- 핵심 원칙:
  - 상위 `MapUiState`는 유지
  - browse 결과 내부에서만 API category/featureType을 map marker model로 변환

#### Step 5. marker/filter 매핑 규칙 확정

- quick filter row는 `featureType` 필터로 해석한다.
  - `TOILET` chip -> `accessibleToilet`
  - `ELEVATOR` chip -> `elevator`
  - `CHARGING_STATION` chip -> `chargingStation`
- place category는 서버 `category` 기준으로 해석한다.
- 현재 map marker visual category가 API와 다르므로, FE 내부 adapter에서 visual priority rule을 둔다.
  - 원칙안:
    - 기본 marker icon은 place category 우선
    - 단, `ETC + chargingStation`처럼 서비스상 의미가 명확한 경우 visual override 허용

#### Step 6. `GET /places/{placeId}` 기반 시설 상세 연결

- marker tap 시 실제 상세를 fetch하고 `facilityDetailSheetState`를 채운다.
- `FAC-01`은 계속 overlay로 유지한다.
- sheet 내부 북마크 상태는 응답의 `isBookmarked` 또는 기존 `BookmarkRepository`와 정합되게 맞춘다.
- `FacilitySetDestinationClicked`는 계속 `PlaceDestination` handoff를 사용한다.

#### Step 7. 검색 API 연동 준비를 함께 마감

- `SearchRemoteDataSource.search()`를 `/places/search` 기준으로 구현한다.
- `SearchViewModel`의 recent destination 저장 시 `placesRepository.getPlaceDetail()`이 실제 응답을 사용하도록 정리한다.
- `matched=false` 결과는 FE contract 재정의가 필요하므로 1단계 안에서 최소 정책을 정해야 한다.
  - route handoff는 좌표 기준으로 허용
  - bookmark는 차단 또는 비노출

#### Step 8. seed/mock 의존 축소

- `FacilitySeedRepository`는 preview/demo/test fallback 전용으로 축소한다.
- production map flow에서 seed browse를 기본 source로 쓰지 않는다.
- repository source policy는 `remote -> local -> mock`을 유지하되, map production path에서 remote 성공 기준을 우선한다.

### 7.3 2단계: 같은 패턴을 route preview / navigation overlay로 확장

- 이번 단계는 실행 계획만 정리한다. 구현 대상은 아님.

#### Step 1. 공유 지도 renderer 추출

- `MapViewport`에서 정리한 provider adapter를 route preview, navigation map에서도 재사용 가능한 수준으로 분리한다.

#### Step 2. route overlay 모델 추가

- marker 외에 polyline, current position, step highlight, destination pin을 그릴 수 있는 overlay model을 정의한다.

#### Step 3. ROUTE-01 preview 적용

- 현재 route preview fallback 영역을 같은 SDK renderer 위에 polyline 중심으로 확장한다.
- map shell/summary/CTA는 그대로 두고 map 레이어만 교체한다.

#### Step 4. NAV-01 진행 지도 적용

- navigation map은 현재 위치 puck, 선택 경로 polyline, next maneuver emphasis를 같은 adapter 패턴으로 확장한다.
- reroute/arrival 상태는 route domain 처리이므로 map renderer는 “표현만” 담당한다.

## 10. 리스크

1. category / featureType 분리 리스크
   - 현재 FE marker model은 seed 중심 category라 실제 API를 그대로 넣기 어렵다.
2. unmatched search result 리스크
   - `/places/search`의 `placeId=null`이 현재 FE contract와 충돌할 수 있다.
3. marker visual rule 리스크
   - `ETC + chargingStation` 같은 케이스는 FE가 별도 시각화 우선순위를 정해야 한다.
4. SDK lifecycle 리스크
   - Compose `AndroidView(MapView)`와 화면 lifecycle 결합을 잘못 처리하면 메모리/black screen 문제가 날 수 있다.
5. 테스트 리스크
   - 실제 지도 SDK는 unit test에서 직접 검증하기 어렵기 때문에 adapter 경계를 명확히 하지 않으면 회귀 검증 비용이 커진다.
6. auth 의존 리스크
   - `/places`, `/places/search`는 인증이 필요하므로 mock/demo/debug mode와 production path 분리가 명확해야 한다.

## Cross-Lane Handoff

### 백엔드 확인이 필요한 항목만 정리

1. `/places/search`의 `matched=false` 결과에서 FE가 route handoff용으로 사용할 안정 식별자 정책이 필요한지 확인
   - 현재 응답은 `placeId=null`, `providerPlaceId`는 존재 가능
   - FE는 route handoff는 좌표 기반으로 가능하지만 bookmark/save 정책은 분기 필요
2. `/places` marker visual 결정을 위해 `ETC + chargingStation` 같은 케이스에 서버가 별도 marker hint를 줄 계획이 있는지 확인
   - 없으면 FE에서 featureType 기반 visual override 규칙을 가진다
3. `/places` 기본 반경/권장 반경 재호출 기준 합의
   - FE는 현재 위치 이동 시 과호출을 피하기 위한 threshold가 필요
4. `/places/{placeId}` 응답에 운영시간/추가 설명이 없다는 전제를 확정
   - FE는 현재 `description` 없이도 `FAC-01`을 구성하도록 정리 가능
5. `featureType` / `category` enum 값의 케이스와 변경 가능성 확정
   - FE mapper 고정 전 최종 enum naming freeze 필요
