# 로그인 필수 전환 FE 정합성 및 구현 영향

> **작성일** 2026-04-27  
> **기준 정책** 팀 회의 결정: 로그인은 선택이 아니라 필수  
> **작성 범위** FE 문서 정합성, 현재 FE 구현 변경 필요 항목 정리  

---

## 1. 결론

팀 회의에서 로그인 필수가 확정되었으므로, 기존 `비로그인 MVP`, `local-first`, `비로그인으로 계속` 전제는 더 이상 최종 기준으로 사용할 수 없다.

FE 기준의 최종 진입 조건은 아래 순서로 정리한다.

```text
앱 실행
  -> 인증 세션 확인
  -> 미로그인: 로그인 화면
  -> 로그인 완료 + profileCompleted=false: 프로필 설정 / 회원가입 완료
  -> 온보딩 미완료: 온보딩 5단계
  -> 인증 완료 + 프로필 완료 + 온보딩 완료: 지도 메인
```

단, `로그인 화면을 온보딩 5단계 앞에 둘지, 뒤에 둘지`는 디자인 시안에 아직 없으므로 `추가 확인 필요`로 둔다. FE 구현 판단은 보수적으로 `인증 세션 확인을 앱 시작의 최상위 gate`로 본다.

## 3. 문서 정합성 충돌

| 항목 | 기존 기준 | 로그인 필수 기준 | 처리 |
| --- | --- | --- | --- |
| 서비스 진입 | 온보딩 완료 후 바로 `MAP-01` | 인증 세션, 프로필, 온보딩 완료가 모두 필요 | FE route map, 코드 컨벤션 개정 |
| 로그인 위치 | 후순위/확장 기능 또는 마이페이지 진입 | 앱 진입 필수 gate | `AUTH-001`, `AUTH-002` 추가 |
| 비로그인 사용 | 핵심 기능 이용 가능, 로컬 저장 중심 | 생산 흐름에서 허용하지 않음 | `비로그인으로 계속`, 게스트 모드 제거 |
| 저장 데이터 | 북마크/자주 가는 길/최근 검색 local-first | 로그인 사용자 서버 데이터가 기준 | repository 기준 개정 필요 |
| 프로필 | 후속 확장 또는 로컬 설정 | `profileCompleted=false`면 핵심 기능 진입 불가 | 프로필 설정 화면 필요 |
| 권한/약관 | 온보딩 local 저장 중심 | 서버 사용자 설정과 동기화 가능성 검토 | 저장 위치 추가 확인 필요 |
| 마이페이지 | placeholder, 로그인/로그아웃 후속 확장 | 로그인 사용자 정보/로그아웃/회원탈퇴 진입 필요 | `MYP-01` 개정 필요 |
| API 인증 | 일부 문서에 Bearer 토큰 존재, FE 미연결 | 인증 인터셉터/토큰 재발급/401 처리 필수 | 네트워크 레이어 추가 필요 |

## 4. 현재 FE 구현 영향

| 파일/영역 | 현재 구현 | 변경 필요 |
| --- | --- | --- |
| `app/navigation/Route.kt` | `OnboardingRoute`, `TopLevelRoute`, `SearchRoute`, `RouteSettingRoute`, `ReportRoute`, `NavigationRoute`만 존재 | `AuthRoute.Login`, `AuthRoute.ProfileSetup` 추가 |
| `app/navigation/AppStartDestination.kt` | `InitSettings`만 보고 온보딩 3단계 또는 지도 메인으로 이동 | `AuthSession`을 먼저 판단하고, 미로그인은 `AUTH-001`로 이동 |
| `app/navigation/AppNavHost.kt` | `settingsRepository.getInitSettings()` 기준 startDestination 결정 | `AuthSessionRepository`와 `SettingsRepository`를 함께 읽어 startDestination 결정 |
| `app/navigation/OnboardingNavGraph.kt` | 기존 3단계 온보딩 완료 후 `Map` 이동 | 최신 5단계 온보딩으로 교체하고 완료 후에도 인증/프로필 상태를 보장 |
| `core/model/InitSettings.kt` | 장애유형/등급/약관 동의만 포함 | 로그인 필수 흐름에서는 `AuthSession`, `profileCompleted`, `selectedUserType`와 역할 분리 |

| `app/AppContainer.kt` | 인증 API, token store, interceptor, auth repository 없음 | `AuthRepository`, `UserRepository`, token provider, 인증 네트워크 구성 추가 |
| `data/repository/BookmarkRepository.kt` | Room 기반 local 저장 | 로그인 필수 기준에서는 서버 북마크 API가 source of truth, Room은 cache/outbox 역할 |
| `data/repository/ReportRepository.kt` | draft/outbox local 중심 | 로그인 필수 앱에서는 세션 상태를 보장한 뒤 제출한다. 단, 제보 API가 계속 익명/인증 불필요인지 Bearer 인증으로 바뀌는지는 추가 확인 필요 |
| `feature/mypage/MyPageScreen.kt` | placeholder 중심 | 사용자 정보, 로그아웃, 회원탈퇴, 프로필 수정 진입 필요 |
| `feature/auth` | 패키지 없음 | `AuthContract`, `AuthRoute`, `AuthScreen`, `AuthViewModel`, social login component 필요 |
| 네트워크 공통 | `Authorization`, `Bearer`, token 재발급 처리 없음 | OkHttp interceptor, authenticator 또는 명시적 reissue flow 필요 |

## 7. 화면명세서 개정 시 반영할 최종 기준

- 로그인은 선택 기능이 아니라 필수 진입 조건이다.
- `비로그인으로 계속`, 게스트 모드, 로그인 없이 지도 메인 진입은 생산 기준에서 제거한다.
- 신규 화면 ID는 `AUTH-001 로그인`, `AUTH-002 프로필 설정 / 회원가입 완료`로 둔다.
- 앱 진입 route 판단은 `authSession -> profileCompleted -> onboardingCompleted -> main` 순서로 정의한다.
- `profileCompleted=false` 사용자는 지도, 검색, 경로, 제보, 저장 기능에 진입할 수 없다.
- 온보딩 5단계 자체는 최신 디자인 기준을 유지하되, 로그인 gate와의 정확한 순서는 추가 디자인/기획 확인 후 화면명세서에 반영한다.
- 북마크/자주 가는 길은 로그인 사용자 서버 데이터가 기준이며, 로컬 저장은 cache/offline/pending 보조 역할로 재정의한다.
- 화면명세서 문서는 현재 요청 범위에서 직접 수정하지 않았고, 이후 개편 대상으로 남긴다.
